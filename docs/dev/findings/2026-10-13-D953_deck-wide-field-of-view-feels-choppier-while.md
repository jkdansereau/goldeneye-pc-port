## D953: wide Field of view feels choppier on the Deck while turning — LOD switches move closer with FovScale — FIXED (v0.6.0)

**Symptom (maintainer, Deck).** At the maximum Field of view (90 deg vertical in the menu = `Video.FovScale = 150`) turning feels choppier than at the default 60 deg, at 60 AND 90 fps; frame times look fine. Maintainer can't name a specific artefact ("it just feels worse", "mostly turning").

**Ruled out (Deck Game Mode, deckrunner, Dam `--script turn`, 45 s, maintainer's v0.6.0 ini, 2 runs each).** Frame delivery is identical at 60 vs 90 deg: 60 fps 0 SLOW frames both; 90 fps ~99% of present gaps in 9.5-12 ms both, softened/exact interpolation decisions the same (pre-softened 285/244 vs 272/235, late exact 4/4 vs 2/1), no extra ROOMCHANGE/REACH/CUT/FALLBACK at 90 deg. Turn speed (uses the game's own fovy), culling (D222), the fog edge (D503).

**Cause (code).** `c_lodscalez` (`currentPlayerSetCameraScale`, `src/game/bondview.c`) is tan(fovy/2)/tan(30 deg) and is built from the RENDERED fovy (D222 `frCullFovY`), so FovScale 150 multiplies every model's LOD distance (`modelUpdateDistanceRelations`, `src/game/model.c`, distance = view-space depth * c_lodscalez) by tan(45)/tan(30) = 1.73: switches move 1.73x closer. The distance is view-space DEPTH, not radial distance, so it changes fastest for objects off to the side while turning — exactly the objects a wide FOV puts on screen.

**Measured (temp probe, LOD-node visibility flips per 600 frames, frames 1200-2400 = the turning part; identical in both runs of each case).** 60 deg: 0 (fix on or off). 90 deg v0.6.0: 400. 90 deg with the fix: 120. One visible model swap is usually 2 node flips. The residual 120 are objects whose depth crosses the authored (60-deg-equivalent) thresholds while turning; at 60 deg they are presumably off screen (not measured; the probe can't tell on/off screen).

**Fix candidate (`fix/d953-fov-lod`, `src/game/model.c`, `#ifdef PORT`, D565 pattern).** Multiply the LOD distance by tan(own/2)/tan(rendered/2), own = `viGetFovY()`, rendered = `c_perspfovy` (what c_lodscalez was built from, so portScaleFovY's clamps and title-screen exemption carry over). Identity whenever the two are equal (all defaults). Video.LodDistance still composes on top. Builds (Windows untested; Linux WSL Ubuntu-24.04 build deployed to the Deck as `~/ge007-v050/ge007.x86_64.d953`).

**Owed.** (1) Maintainer feel test that discriminates the hypothesis with NO build: v0.6.0 at FOV 90, `LodDistance` 200 -> ~350 (cancels the 1.73x; roughly what the fix does), then higher (the residual edge swaps). If that removes the feeling, LOD is the cause; choose between this fix, an automatic LodDistance boost at wide FOV, or both (the residual 120 suggests the fix alone may not be 100%). If it does not, LOD is not the cause. (2) Then Windows build + per-patch golden diff (identity at defaults).

**Pass 2 (2026-10-13 evening): all render consumers of c_lodscalez, and a measurement on Surface.** Besides model LOD, two render paths scale with the rendered FOV: the prop/guard fog fade (`propobj.c` `chrobjFogVisRangeRelated`) and the prop fog-range visibility test (`sub_GAME_7F054C58`). Their D222/D218 compensation divides by `portDrawDistanceMultiplier()`, which was FOV-linked only through `Video.DrawDistanceAutoFov`; that became a legacy option (off), so the multiplier is the flat Video.DrawDistance and at FovScale 150 props faded and popped at x0.58 the default-FOV distance. All three now use one helper, `portLodScaleOwnFov()` (`port/src/video.c`, tan(own/2)/tan(rendered/2), cached; 1.0 at defaults). AI paths were already corrected (D565); frustum culling keeps the rendered FOV (D222). Turning is not FOV-scaled (bondview2.c uses the game's fovy; `input.c` only declares portScaleFovY).
Measured (Windows, Surface 1, 1280x800, 60 fps, same scripted look left/right, temp probe from frame 400, since removed): LOD flips 37 / 37 / 37, fade-state changes 1 / 1 / 1, visibility flips 0 / 2 / 0 (FOV 100 / 150 / 150 + fix). Evaluations in the partial fog fade: 256 / 0 / 246, so at max FOV without the fix the props that sit half-faded in Surface's fog at the default FOV were fully invisible; the fix restores them. **On Surface none of these change while turning, so they do not explain the maintainer's "default FOV feels smoother at any fps" (Deck, Surface, 90 fps, D954 build).** Remaining FOV-dependent factor, by code: image-level. At bilinear (the Deck ini: TextureFilter 1) only textures the game flags as mipmapped get mips (`gfx_opengl.cpp` upload), the rest are minified with plain GL_LINEAR, and a 90-deg vertical FOV minifies every surface ~1.7x more, so more of the frame shimmers while the camera moves; thin geometry goes sub-pixel likewise (MSAA 2x). Plus the rectilinear stretch at 116 deg horizontal (edge vs centre screen speed 3.6x, against 1.9x at the default). Discriminating test, no build: FOV 90 with Texture filter = Trilinear (mips on every texture).
Maintainer (same evening) rejects the texture lead: "models/objects kinda lag behind... like tearing except nothing is tearing... just seem to update not at the right speed." That matches the 90 fps path: in-between passes blend only the camera (D578, D954), so object motion (props and matrix-skinned chrs) still steps at the 60 Hz tick inside a 90 Hz picture. Plan D955 (object-motion interpolation keyed by (Model*, joint), no game hooks) is reviewed (go with changes) and staged; Stage 0 is instrumentation only. Still unexplained: why max FOV feels worse than the default at the same fps. Open lead: GE's wall-clock tick step (frametiming.c) taking 2-tick steps more often at wide FOV on the Deck; never measured (Deck summaries record presents and draw time only); `GE_D193=1` logs render frames vs sim ticks per second.

**Pass 3 (maintainer, Deck, 2026-10-13).** Surface building windows flickered white while the camera moved, at 60 and 90 fps, at FovScale 150: the prop fog fade (`chrobjFogVisRangeRelated`, view depth `zDepth`) was pulled to x0.58, so half-fogged window props went fully invisible; pass 2's `portLodScaleOwnFov` fixes it (maintainer-confirmed on the combined D953+D954+D955 build). Texgen ruled out (probe: Surface's texgen draws keep constant UVs while the camera moves).

**Status.** FIXED (v0.6.0).
