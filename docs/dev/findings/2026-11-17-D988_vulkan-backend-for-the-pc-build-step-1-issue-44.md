# D988

## D988: Vulkan backend for the PC build, step 1 (issue #44) -- window, instance, device and swapchain; each present clears to a fixed colour -- BUILT + RUN 2026-11-17 (Windows cross-build, RTX 5070: clear colour read back from the window, clean exit; validation layer on: 0 errors)

**Goal.** Issue #44: a Vulkan `GfxRenderingAPI` beside GL (Windows, Linux, macOS through MoltenVK), selected with `GE_RENDERER=vk`; GL stays the default until Vulkan matches it. The Switch keeps deko3d. This entry covers step 1 of the issue.

**Change (port render layer only, no game code).**
- `port/fast3d/gfx_vulkan.cpp` / `.h` (new, compiled only with `GE_VULKAN`): volk opens the loader at run time (`volkInitialize`), so the binary links no Vulkan library. Vulkan 1.3 core is required (dynamic rendering, synchronization2; extended dynamic state is core in 1.3). The device is the first usable discrete GPU, then integrated. `VK_KHR_portability_enumeration` / `VK_KHR_portability_subset` are enabled when offered (MoltenVK). The swapchain is UNORM (as GL's default framebuffer), FIFO for swap interval >= 1, otherwise IMMEDIATE, then MAILBOX, then FIFO; it is recreated when the drawable size changes, on `OUT_OF_DATE` / `SUBOPTIMAL`, and when the swap interval changes. Two frames in flight (command pool, fence, acquire semaphore each); one render-done semaphore per swapchain image, so a semaphore is never re-signalled while a present still waits on it.
- Present (`gfx_vulkan_present`, the external-present hook): acquire, a dynamic-rendering pass that clears to (0.10, 0.18, 0.32), barrier to `PRESENT_SRC`, submit, present. The rendering API calls are accepted and tracked (programs from `gfx_cc_get_features`, texture / mesh ids, framebuffer sizes) but draw nothing yet. `mesh_supported` is false, `stream_begin` returns NULL (the decoder fills its own buffer), and `gfx_skyplus_failed = 1` so `skyplus.c` draws GE's own sky.
- `gfx_vulkan_park`: device idle, swapchain, frames, device, surface, messenger and instance destroyed; logs the validation error / warning counts.
- Validation: `VK_LAYER_KHRONOS_validation` plus a debug-utils messenger whenever the layer is installed; `GE_VKVALIDATE=0` turns it off.
- `gfx_sdl2.cpp`: the D973 external-present hooks (present, dimensions, park, swap interval) now build on the PC too (`__SWITCH__ || GE_VULKAN`). The GL window and context creation moved unchanged into `create_gl_window`; `create_vk_window` makes an `SDL_WINDOW_VULKAN` window with no GL context. `drawable_size` uses `SDL_Vulkan_GetDrawableSize` for that window.
- `video.c`: `GE_RENDERER=vk` -> `gfx_vulkan_probe` (a throwaway instance looks for a usable 1.3 device) -> the Vulkan API and hooks; no usable driver -> GL with a warning. `GE_PCDUMP` and screenshots are skipped with one warning (no readback of the presented image yet, issue step 3/4). The low-end renderer check reads the Vulkan device name.
- `gfx_pc.cpp`: the backend-extras table (FXAA, GE+ sky, D578 present slots, rewind, PERFSTAT) is now built on the PC with `GE_VULKAN` too; the Vulkan entries are stubs. The FXAA slot is NULL off the Switch (FXAA is Switch-only).
- Build: `GE_VULKAN` (CMake option) is on when the Vulkan headers are found off the Switch. `volk.c` is its own static target (`ge_volk`) without the decomp's shadow headers (`port/shim/stddef.h` hid `NULL`) or the forced `versioninfo.h`. `Dockerfile.build`: `libvulkan-dev`, `glslang-tools`. `Dockerfile.windows`: `vulkan-headers` (copied into the MinGW sysroot) and `glslang`. volk 1.4.304 (MIT) declared in `NOTICE`.

**Verified.** Windows cross-build (Docker), `GE_RENDERER=vk GE_QUITFRAME=600 -level_09` on an RTX 5070 (the AMD iGPU is listed and skipped): swapchain 1224x918, 3 images, FIFO; 600 frames at 60 Hz; the window's centre pixel read with `PrintWindow` is (25, 46, 82) = the clear colour; exit code 0 after `VK: backend parked`. The same build without `GE_RENDERER` runs GL as before. With the validation layer on: 0 errors; the 3 warnings are loader messages about a third-party overlay layer's name (GOG Galaxy), not about the port.

**Validation without the SDK.** The loader only needs `VkLayer_khronos_validation.dll` and its `.json` manifest in one folder named by `VK_ADD_LAYER_PATH=<folder>`; no SDK install. Working source: the MSYS2 packages, downloaded straight from `repo.msys2.org/mingw/mingw64/` (no MSYS2 install; `tar --zstd -xf`, e.g. inside the Windows build image): `vulkan-validation-layers` (1.4.363.0 verified) and `spirv-tools` for the layer, plus `libstdc++`, `libgcc` and `libwinpthread` because the game links libstdc++ statically and ships no `libstdc++-6.dll`. Copy every `mingw64/bin/*.dll` and the `.json` into the folder. Without the runtime DLLs the layer fails to load with Windows error 126. Do NOT use Fedora's `mingw64-vulkan-validation-layers` 1.4.321: it crashes on Windows (call through a null pointer inside its `libSPIRV-Tools-opt.dll`) right after swapchain creation, before any port code runs. The Khronos GitHub releases ship Windows binaries only as `nightly`.

**Layer that does not load.** When the manifest is found but the DLL fails to load, `vkCreateInstance` returns `VK_ERROR_LAYER_NOT_PRESENT`; `create_instance` then retries without validation and logs a warning, instead of a fatal error (checked with a folder holding the manifest only).

**Next (issue #44 step 2).** Vertex ring and `draw_triangles`, textures and samplers, the combiner shaders as SPIR-V (a Vulkan flavour of `tools_pc/dkshgen`, compiled with `glslangValidator` at build time) and the uber-shader fallback; framebuffers as images.

**Confidence.** High for what step 1 covers on Windows / NVIDIA. Linux runtime, AMD / Intel drivers, MoltenVK and window resize were not run.
