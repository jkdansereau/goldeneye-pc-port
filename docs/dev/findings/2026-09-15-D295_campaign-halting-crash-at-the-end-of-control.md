## D295 — Campaign-halting crash at the end of Control Center on 00 Agent difficulty, then a crash on every subsequent relaunch/resume (GitHub #87, user campaign playtest).

**Campaign-halting crash at the end of Control Center on 00 Agent difficulty, then a crash on every subsequent relaunch/resume (GitHub #87, user campaign playtest).** Reported directly as [GitHub issue #87](https://github.com/jkdansereau/goldeneye-pc-port/issues/87) (not yet actioned there — this repo is under a push freeze to `main`, per M-139b; issue itself was filed by the user independently and needs no push). User played the campaign on 00 Agent difficulty through the end of Control Center; at that point the game crashed, and it now **crashes on every subsequent launch/resume attempt** — i.e. this is not a one-off, it reproduces deterministically from the user's current save/session state, unlike D289 (Dam, non-reproducible) or D286 (Caverns freeze, self-recovering). That "crashes every time now" detail is the most actionable lead: whatever corrupted is either the EEPROM save file (`data/ge007.eep` — see the D255/D3x pointer-truncation class, and the D284 PRNG-state class) or some other persisted/level-transition state that Control Center's completion writes, and it's now poisoning every subsequent boot into that save slot, not just the original crash frame.

**Also reported, same playtest, possibly related:** progressively worsening audio corruption starting around Streets and continuing through to the Control Center crash — user's own framing is "Idk if that contributed to it somehow." Streets → Depot → Control Center is roughly the mission order in this stretch; if audio state is shared/leaked across level transitions (cf. D204 tempo drift, D202 stuck door loop, D285 audio-thread SIGSEGV — all real, distinct bugs already found in the audio-thread class this session/prior sessions), a slow audio-side corruption building up over several levels and finally taking down Control Center is plausible, but **nothing here confirms causation** — could equally be an unrelated coincidence of timing.

**Status (from §F table):** OPEN — not investigated. No crash log, `bt full`, or repro steps captured yet. **Next steps, in order:** (1) get the user's `ge007.crash.log` (or a `gdb bt full` under `debug.ps1`) from the actual crash, plus their `data/ge007.eep` if they're willing to share it — a corrupted-save reproduction would be the fastest path to a fix and would explain the "crashes on every relaunch" persistence; (2) if the save file also crashes cleanly on a fresh debug build, that confirms save-state corruption over a fresh code bug; (3) chase the audio-degradation report only if it turns out to correlate with the crash (e.g. an audio-thread crash address) — don't spend time on it as a separate lead until then.

**M-146 (2026-09-16, same day): artifacts obtained + platform + version pinpointed; likely already fixed by v0.2.2, unconfirmed.** User supplied `ge007.crash.log`, `audiotrace.log`, and `data/ge007.eep` (via the GitHub issue + a G-Drive link for the save).

- **Platform confirmed Windows, from the crash log format itself, not inference.** `port/src/crash.c` emits totally different output per platform (`#if PLATFORM_WINDOWS` vs `#elif PLATFORM_LINUX`). The user's log opens `EXCEPTION: 0xc0000005` (an NT `STATUS_ACCESS_VIOLATION` code) and includes `MxCsr=... x87CW=... x87SW=...` (the x86 `CONTEXT` FPU state) — both Windows-only; the Linux path prints `SIGNAL: 11` and never emits FPU control-word fields. `FAULT ADDR: 0000000000000000` — a genuine null-pointer dereference, PC `0x1400797c1` (module base `0x140000000`, RVA `0x797c1`, unsymbolicated — no matching build/PDB available to resolve it further).
- **Version pinpointed by ancestry, not the crash log (no version string is captured in `ge007.crash.log` today — worth adding one).** Issue #87 was filed 2026-09-16 01:13 UTC; `v0.2.2` was tagged 2026-09-16 13:13 UTC, ~12h *later* — v0.2.2 did not exist yet, so the user was on `v0.2.1` (the latest public release at report time). `git merge-base --is-ancestor` confirms both `1ba83ba4` (D255 fix) and `1970ab37` (D285 fix) are **absent from `v0.2.1`, present in `v0.2.2`**.
- **D255 is the leading candidate**, on shape + level content: D255 was a 32-bit-pointer-truncation bug (`Model*` read through a mistyped 4-byte `chrflags` alias) that on PC either dereferences garbage or, when the truncated low bits land on zero, crashes exactly like a real NULL — matching this log's `FAULT ADDR: 0`. Control Center's own briefing (`assets/obseg/brief/UbriefcontrolZ.c`) lists **"Destroy armored mainframes"** as an objective — an explosion-triggered object-destruction event, the same `vtxstore_fix_refs` code path D255 patched. Not proven (no symbols to confirm the crash PC actually lands in `vtxstore_fix_refs`), but a strong circumstantial fit.
- **D285 fits the reported audio-corruption symptom** (an unlocked shared-list read racing a locked writer in `sndHandleEvent`) but less specifically fits the null-fault shape.
- **New, separate, still-OPEN issue found while reading `audiotrace.log`:** it is nothing but a wall of `[EVTQ-DROP]` lines (1089 total) — `src/libultra/audio/event.c:92`'s D202-era diagnostic, which logs unconditionally (no env gate) whenever the audio event free-list (`evtq->freeList`) is exhausted. This fires continuously in the user's log, i.e. **real evidence the event pool was genuinely, sustainedly exhausted during their session** — distinct from D285 (a race, not a leak) and not fixed by either v0.2.2 patch. The probe itself is also a minor release-hygiene bug (D202 cleanup was supposed to remove it — see the D202 M-2x closeout note — and never did; it's still live on `release/v0.3.0`/HEAD today, silently writing an unbounded log file in shipped builds).
- **Repro attempt on current `release/v0.3.0` HEAD (already carries the v0.2.2 fixes) did NOT reproduce the crash**, but this is a partial result, not a clean disproof:
  - Front-end/mission-select/file-select screens with the user's real `ge007.eep` loaded (`GE_STARTMENU=5/7`, `tools_pc/debug.ps1`): no crash, save data reads fine.
  - **User live-played Control Center start-to-finish at the correct difficulty** (`-level_23 -hard2` — `src/boss.c:396-401`'s native N64 debug switch for `DIFFICULTY_00`, not a bare `-level_23` which silently defaults to Agent and would NOT have been a faithful repro) with the real save loaded, under `tools_pc/debug.ps1` (gdb-attached). Completed the level (with cheats enabled partway through) — **no crash**, consistent with "v0.2.2 already fixed it" but not a controlled A/B, since the branch tested already has both fixes applied. User separately reported drone-gun stutter during this playthrough — logged as **D296**, with the debug-harness caveat noted there.
  - **Next, concrete: user is pulling the actual `v0.2.1` release artifact and replaying the same save file on it.** If it crashes there and not on current HEAD, that's the controlled confirmation this finding needs to close as FIXED-by-v0.2.2; if it does NOT crash on `v0.2.1` either, D255/D285 are not the cause and this stays open for a fresh investigation (get a build with matching symbols/PDB from whoever can reproduce it, to actually resolve RVA `0x797c1`).

**M-147 (same day, 2026-09-16): RETRACTING the D255/D285 hypothesis above — real root cause found via symbols, and it's a different bug family entirely.**

- User pulled the actual `v0.2.1` release artifact (`goldeneye-pc-port-0.2.1-win64`, which ships full DWARF debug info) and reproduced with the real save: **crashes deterministically right after the intro, same `EXCEPTION: 0xc0000005` / `FAULT ADDR: 0000000000000000` / same crash PC `0x1400797c1` as the original report** (confirmed by direct comparison — this is the exact same crash, not a new one).
- `addr2line -e ge007.x86_64.exe -f -C -p 0x1400797c1` resolves cleanly: **`langGetJpnCharPixels` at `src/game/language.c:320`.** A real, symbol-confirmed NULL dereference, not a guess.
- **Mechanism:** `g_JpnCacheCacheItems` (`language.c:29`) is a global pointer, allocated only inside `langInit()` when `j_text_trigger` is true (`language.c:247-249`, gated on Japanese-language mode). `langGetJpnCharPixels()` (`language.c:303`) has **no NULL check** before indexing it at line 320. It is called unconditionally — **not gated by `j_text_trigger` or the actual selected language** — from `textRenderGlyph`'s string-draw loop (`src/game/textrelated.c:475-499`) for *any* character byte with the high bit set (`*text >= 0x80`). So any rendered string containing a stray high-bit byte null-derefs immediately, on any region build, regardless of language setting. This is the same general shape as the already-documented `D50.5` "Legal-screen UB exposure" nearby in this file (a read that's harmless-by-luck on N64 hardware, fatal on PC) — a good candidate for the same style of minimal `#ifdef PORT` defensive guard, not a game-logic change.
- **Confirmed save-specific, not a stock v0.2.1 regression:** user re-ran the same v0.2.1 binary with a fresh (no-save) `data/` and it ran fine — the crash needs this specific save's corrupted content.
- **The wrinkle that keeps this open rather than closing it as a clean v0.2.1-only bug:** `src/game/language.c`, `textrelated.c`, `file2.c`, `file.c`, and `token.c` are **byte-identical** between the `v0.2.1` tag and current `release/v0.3.0` HEAD (`git diff v0.2.1 HEAD` on those five files shows nothing but two unrelated diagnostic-probe additions in `front.c`/`libultra.c`). Yet replaying the exact same save on a HEAD build through a full, real boot (no `GE_STARTMENU` shortcuts, 90 s window, `tools_pc/debug.ps1` gdb-attached) **did not crash.** Since the code path itself is unchanged, the most likely explanation is that the *actual* defect is upstream of `language.c` — almost certainly an out-of-bounds/garbage read while formatting save-derived display text (leading guess: the packed completion-time/percentage fields, `geSaveGetTime`-style bit-unpacking in `port/src/libultra.c`/`src/game/file2.c`, or a folder/mission-select stat string built from `unlocked_cheats_*`/`times[76]`) — and *which* garbage byte lands there is sensitive to the binary's memory layout, which differs between the two builds purely from the ~100+ unrelated intervening commits. **This means the underlying bug is plausibly still live on HEAD, just not triggered by this specific save on this specific build — not something v0.2.2 fixed on purpose.** D255/D285 are unrelated; both are real, correctly-identified, already-fixed bugs, they just aren't this one.
- **Next steps, in order:** (1) add a temporary `#ifdef PORT` probe at `language.c:319` logging `codepoint`/`i` plus the 8–16 bytes around the source string pointer whenever `g_JpnCacheCacheItems == NULL`, then replay the v0.2.1 repro (or try harder to trigger it on HEAD — a longer soak, or navigating to the specific folder/mission-select row that displays this save's Control Center/Caverns stats, since our 90 s window only proved the *default* landing screen doesn't trigger it) to catch the actual string content live; (2) once the upstream OOB read is identified, the real fix is there, not just a defensive NULL guard in `language.c` (though that guard is also cheap, safe, and worth adding regardless, matching the `D50.5` precedent, since a malformed/third-party-corrupted save should degap gracefully rather than crash even if the deeper cause isn't found yet); (3) do NOT close this finding as "fixed by v0.2.2" — that was this session's own wrong first guess, corrected here.

**M-148 (2026-09-16, independent re-verification session): FULLY ROOT-CAUSED end-to-end; verdict OPEN — the bug is live on `release/v0.3.0` HEAD, reproduced there from scratch. The M-147 "upstream OOB/garbage read" guess is retracted: no OOB exists.** Every claim below was re-derived from primary evidence (crash logs, both binaries under gdb, the user's actual `ge007.eep`, compiled-C CRC reproduction) rather than trusted from prior write-ups.

- **The user's save is NOT corrupted — it is a valid *pre-D284* save.** `fileValidateSaves` (`file2.c:544`) CRCs each slot over `&save->completion_bitflags .. save+1` (slot bytes [8..96), 88 bytes) via `fileGenerateCRC` (`src/game/crc.c`), which runs `randomGetNextFrom` off a **local constant seed `0x8F809F473108B3C1`** — *not* `g_randomSeed`. Reproduced that function in compiled C from both the pre-fix (`git show 0de99b4d^:port/src/random.c`) and current-HEAD `random.c`: **the pre-D284 (v0.2.x-shipped) PRNG reproduces all five stored slot CRCs bit-exact; the fixed PRNG matches zero.** (Pure-Python model `tools_pc/d295_crc.py` — gdb scripts/outputs in `scratch/d295/` — now matches the compiled C exactly — two transcription bugs found and fixed along the way: the seed is updated *in place* by `randomGetNextFrom(&polynormal)` each step, and `a2 = a2 >> 0x1f` / `a3 = a2 >> 0x14` are plain `dsrl`, not the `*32` helpers.) Consequence: on any post-fix build, first launch with this save wipes all five slots (confirmed live, `GE_SAVELOG=1`: every slot `BAD -> RESET (progress wiped)`), so **the reported crash does not reproduce on HEAD with the unmodified artifact — but that is a side effect of the wipe, not a fix.**
- **This disproves the D284 commit/entry claim "savegames are unaffected (seed isn't save state)"** — see the correction appended to `## D284`. `fileGenerateCRC`'s stream *is* persisted state: every stored slot CRC is a fingerprint of the PRNG implementation that wrote it. **Release-blocker-class regression for v0.3.0: every existing player's entire campaign progress is silently erased on first launch.** Needs its own D entry + a decision (dual-CRC acceptance / one-time migration / at minimum a loud release note) — flagged here, not unilaterally filed.
- **The crash mechanism (M-147) is confirmed end-to-end and is the whole story; there is no upstream OOB.** `front.c:2616` declares `char difficultytext[4]`; the file-select folder panel does `strcpy(difficultytext, "00 Agent")` (9 bytes incl. NUL) + `strcat("\n")`. gdb on **both** the v0.2.1 artifact and a HEAD debug build confirms the stack layout: `&textpos.p[0] == &difficultytext + 8`, so the `\n` lands on the y-coordinate's low byte and the NUL one past it; the subsequent `textpos.p[0] = floor(folderpos2d.f[1]) + 0x15` store then clobbers `\n` with y. Observed y values across window geometries: **128 and 143 — both ≥ 0x80**, i.e. the fatal case is the *normal* one here. `textRender` (`textrelated.c`, `-funsigned-char`) then scans a byte ≥ 0x80 → JPN glyph path → `langGetJpnCharPixels` (`language.c:320`) dereferences `g_JpnCacheCacheItems`, which is NULL outside Japanese mode on PC. Note: on N64 **non-JP builds this pointer is likewise unallocated** (`langInit` allocates it only when `j_text_trigger`, i.e. JP) — so the crash potential is decomp-native, not a port artifact; the reason it (apparently) never manifested on N64 is that at native geometry `y = floor(folderpos2d.f[1]) + 0x15` presumably stayed < 0x80 (unverified from here), whereas PC window geometry puts y at 128/143 in the observed cases. The overflow itself is decomp-faithful original behavior. `"007"` (4 bytes) and `"Agent"` (6) fit or stop before offset 8 → safe; only `"00 Agent"`/`"Secret Agent"` as a folder's highest completed difficulty reach the fatal byte. (`missiontext[18]` one line above has the same class: `"Mission Cuba.Control Center\n"` is 29 bytes — flagged for review, not separately instrumented.)
- **The M-147 "OOB read of save-derived stat text" guess is retracted — verified against source:** `fileGetSaveStageDifficultyTime` (`file2.c:230`) special-cases `DIFFICULTY_007` *before* any bit math — it returns constant `0x3FF` if `fileIs007ModeUnlocked(folder)` (the slot's `flag_007` bit, or all 20 levels completed on 00 Agent) else 0; the high bit region (offsets 600–790 of a 608-bit `times[]`) is **never read**, and the setter (`fileSetDifficultyStageTime`) excludes 007 (`difficulty < DIFFICULTY_007`), so it's never written either. No OOB, no build-layout sensitivity in the game code. The v0.2.1-vs-HEAD difference was entirely the CRC wipe above: v0.2.1 accepted the save (old PRNG) → folder 1's highest = 00 Agent (`flag_007`=0, 00-Agent 16/20 levels → not 007-unlocked) → `"00 Agent"` rendered → crash; HEAD wiped the save → nothing rendered → no crash.
- **DECISIVE HEAD REPRO (bug is live on v0.3.0):** recomputed the user's five slot CRCs with the *fixed* PRNG (`d295_crc.py`, data-only patch of the artifact — no code probes), placed it in `data/`, ran HEAD unattended 80 s: `GE_SAVELOG` shows all five slots **OK** (progress retained), then `EXCEPTION: 0xc0000005`, `FAULT ADDR: 0x0`, register state byte-identical to the user's v0.2.1 log (`Rax=2 Rcx=0 Rdx=1 Rsi=0xffffffff Rdi=0`); `addr2line` on the HEAD binary → **`langGetJpnCharPixels` at `src/game/language.c:320`**. Repro log saved as `ge007.crash.log.head-repro-M148` in the issue-artifacts folder. `data/ge007.eep` restored to the user's original artifact afterwards (md5 `76e18aa4…`).
- **M-149 (fix landed + verified):** both signed-off items applied and verified on `release/v0.3.0`: (a) `port/src/main.c` seeds `g_JpnCacheCacheItems`/`g_JpnCharCachePixels` from static port buffers before `osStartThread` (exact `langInit` construction, `#include "game/language.h"`, `_Static_assert` on the pixel-stub size; reviewer-caught bugs fixed pre-apply: the `0xC000` bitfield sentinel was wrong — eliminated in favour of field assignment — and a stale `sizeof(jpnItems)==0x100` assert would have hard-failed the build, dropped); (b) `src/game/front.c` widens `difficultytext[4]`→`[32]`, `missiontext[18]`→`[32]` under `#ifdef PORT` (D8 class; N64 build keeps decomp sizes — the decomp author's own comment at front.c:2549-2550 already flagged this buffer as "likely incorrect"). Verification: clean rebuild; **the exact previously-crashing input** (user's save re-stamped with post-fix CRCs via `tools_pc/d295_crc.py`) now runs 80 s unattended with all five slots OK, no crash log — vs the byte-identical register-state NULL deref before the fix; user's original artifact still boots cleanly (takes the D297 wipe path, no crash); 21/21-level `tools_pc/level_sweep.sh` PASS. `data/ge007.eep` restored to the original artifact (md5 `76e18aa4…`) — **note: every game launch rewrites `data/ge007.eep`, so the sweep clobbered the restoration that preceded it; the restore+hash check was re-run after the sweep and again at review time.**
- **Verdict: FIXED (M-149)** for the crash itself; the companion save-wipe regression is tracked separately as **D297** (release-blocker, migration shim pending). History — pre-fix, any v0.3.0 player who completed an 00-Agent (or Secret-Agent) level — their save then validates fine on the post-fix PRNG — would crash at file-select on next launch in any window geometry where the folder y ≥ 0x80 (the common case observed here). Fix plan, **signed off by user 2026-09-16** (both items go; review order: crash-fix bundle first, migration shim separately): (a) *port-side defense-in-depth, rule-2-clean:* seed `g_JpnCacheCacheItems`/`g_JpnCharCachePixels` from static port buffers before `mainproc` starts (non-JP mode only) so a stray high-bit byte takes the normal cache-miss path (romCopy from the JP font segment → garbage glyph) instead of NULL-deref — design validated: `langTick` is `j_text_trigger`-guarded, `langInit` non-JP never touches these, no race; (b) *game-side, D8-class layout correction:* enlarge `difficultytext[4]` → `[16]`, `missiontext[18]` → `[32]` under `#ifdef PORT`. Both are small. Scope note for the migration shim: `fileValidateSaves`'s block-0 `smallSave` CRC (file2.c:512-535) needs **no** migration — `SAVEFLAGS_SET(FOLDER3, SAVESLOT1, BOND_CONNERY, FALSE)` = 0x42 and any in-use save has a different header byte (user's: 0x57), so it takes the "customised file" branch and is factory-reset on every load by design (N64-faithful); only the 5 slots carry user data. The separate v0.3.0 save-wipe regression (D284 side effect, above) is a second, independent release-blocker candidate and should be filed/decided on its own.
