## D318 — Facility (regular play path): after Objective C (destroying the bottling tanks) completes, Ourumov freezes and does not shoot Trevelyan as he should (user report, 2026-09-18).

**2026-09-23 correction (D329):** the pin is a tick-granularity divergence, not a platform-invariant lock. It persists only at 1 sim tick per rendered frame (the port at 60 fps); a single frame of 2 or more ticks (GE's normal N64 regime) breaks it. Lockstep A/B (GE_D318B_CLK) on ai_19 and ai_9: clk=1 pins every time, clk=2 never confirms. Earlier WSL wall-clock pin rates are uncalibrated (mixed clk 1-6). See D329.

**Reported (user, 2026-09-18):** on Facility (`-level_34`), following the **regular play path**, Ourumov **freezes up and will not shoot Trevelyan when Objective C — destroying the bottling tanks — is completed**. The user states this is **definitely a bug** despite prior agent conclusions to the contrary.

**Contradicts D263's resolution.** D263 (v0.2.1) closed the same surface symptom as "not a port bug — proximity/LOS-triggered exactly as on N64", verified via a *teleport probe* that dropped Bond 65 units from Trevelyan and confirmed the full chain incl. the execution shot firing. But that verification was **synthetic** (teleport, not the authored play path), and D263's own refinement already noted the trigger is "significantly sensitive to Bond's precise location" and "not confirmed byte-identical to N64 for every approach". This report reaches the beat via the **authored objective sequence** (Objective C = bottling tanks destroyed) and sees Ourumov frozen with no shot — a materially different entry point than D263 tested. **Do not re-assert the "not a bug / finicky trigger" conclusion from D263 without fresh evidence from this specific path.**

**Investigated (2026-09-18/19): RESOLVED — as-authored latent race, faithfully reproduced by the port (NOT a port bug); port-side deadlock watchdog added (`port/src/d318watchdog.c`).** D310/D311 ruled out (no interaction). D263's mechanism map stands; this is a *different* failure mode than D263 tested — a derailment race, not the proximity trigger.

### Scene graph (byte disasm of ai_22, 384 bytes; `assets/obseg/setup/UsetuparkZ.c`)

Ourumov = chr 78 on list 0x0417 (ai_22). Key offsets: off=38 pre-aim at Trevelyan (`actor_aim_at_actor`, TARGET_AIM_ONLY|TARGET_DONTTURN → attacktype 0x64); off=44 gate-B wait loop (gas bit 0x04 → combat, 0x40 → flee, Bond-miss → combat, surrender 0x20 → dialogue cascade); off=72 dialogue cascade (~1320-tick timers) → off=272 label 0x13 = the execution shot `chr_hit_body_part_with_item_damage(0x43, 0x08, 0x06)` (headshot on chr 67); **off=302 label 0x2a** (combat section, reached when a gas/combat bit lands mid-monologue): off=304 Trevelyan-exists? → **off=307 `actor_fire_or_aim_at_target_update`** (succeeds only while ACT_ATTACK + AIM_ONLY|DONTTURN: sets attacktype/entityid + endframe, returns TRUE → off=321) → else falls to off=315 aim/fire at BOND → **off=321 label 0x01**: sleep → off=324 `if_guard_has_stopped_moving` (→ off=328 headshot on pass) → else loops back to 321.

### Root cause chain (all links byte-matched ROM logic)

1. **Pre-aim hold.** During the monologue c78 pre-aims at kneeling Trevelyan (atk=0x64). `chrlvInitActAttack` picks a RANDOM variant from the aim-animation group (`randomGetNext() % len`) and `modelSetAnimation`s it with `animlooping=0`.
2. **The hold pose is a permanent anim pin.** The aim anim plays to its endframe H (the hold frame). With `animlooping==0`, `modelTickAnim`'s wrap logic is inactive; when the frame reaches endframe, `modelConstrainOrWrapAnimFrame` clamps **both** `framea` and `frameb` to `ceil(H)` (`if (0 <= endframe < frame) frame = ceilFloatToInt(endframe)`), so `framea == frameb`, and the tail of `modelSetAnimFrame2WithChrStuff` (`if (vb == va) { animframe1 = va; }`) then discards all sub-frame progress: the model is pinned at H forever. That is how a hold pose works by design — normally something else changes the attack state next.
3. **The derail.** Objective C (bottling tanks) leaks gas → ai_42 sets obj bit 0x04 (~300 ticks after the leak). If that lands while c78 is in the pre-aim hold, ai_22 derails to section 0x2a and off=307's update command SUCCEEDS: attacktype becomes 0x04, entityid becomes Trevelyan (67), and `chrlvAttackActionRelated` sets a NEW endframe from the variant's recoil/shoot start — **but it never calls `modelSetAnimation`**. The model stays pinned on the aim-hold pose.
4. **The branch (set by the random variant from step 1):**
   - new endframe ≤ H: next tick, `chrlvTickAttackCommon`'s `endframe <= frame` block fires and its unk31 path (`chraction.c:7209`) calls `modelSetAnimation` again → pin broken → anim advances into the shoot window → c78 live-fires Trevelyan → he dies (~230 ticks) → attack sequence completes → ACT_STAND → the off=324 stop check passes → scene continues (combat state).
   - new endframe > H: **nothing ever calls `modelSetAnimation` again** (probe-verified: zero calls in frozen runs). Frame stays pinned at H < shoot_start, c78 never fires, Trevelyan never dies, and the off=324 stop check (`chrHasStoppedOrPatroling`, TRUE only for ACT_STAND/ACT_ANIM/ACT_PATROL) can never pass while c78 is in ACT_ATTACK → **PERMANENT SOFTLOCK**.

### Evidence (probe runs, `scratch/d318_*.log`)

- `modelTickAnim` per-call trace: frozen state ticks every frame (`numticks=1, speed=0.68`) but `animframe1` is byte-identical tick to tick (e.g. 19.00 → 19.00) — the pin is in the model layer, not the AI/attack state machine.
- `modelSetAnimation` funnel trace: frozen runs have **zero** calls post-derail; escape runs' unpin call resolves via addr2line to `chrlvTickAttackCommon` (chraction.c:7209, the unk31 path).
- Pre/post-derail contrast: frozen run pinned at 19.00/end=19.00 → post-derail end=24.00 (24 > 19 → never crosses); escape run pinned at 22.00/end=22.00 → post-derail the unk31 path re-inits at startframe=22 (end ≤ frame) → advances 24→27→44, c67 takes damage, dies t≈2930-2960.
- Non-determinism is by design: the variant pick in step 1 is `randomGetNext()`; forced-bit repros froze ~2/3 of runs. The organic path (user's report; playtest2) hit the frozen branch with no artificial forcing.

### Classification

**As-authored latent race, not a port bug.** Every link — ai_22 flow, the update command's missing re-init, the `framea==frameb` pin, the ACT_ATTACK-gated stop loop — is byte-matched ROM logic.

**N64 manifestation — CORRECTION (2026-09-22, user challenge).** The earlier claim "the N64 has the identical race and the identical unrecoverable softlock" was *inference* from byte-matched logic, never observation — we cannot instrument an N64. The user's empirical prior (and ~30 years of community play with no such known bug) is that guards do **not** freeze on real hardware. For that to hold, the derail must effectively never occur on N64 — i.e., the gas bit never lands inside c78's pre-aim hold window there. But that window is player-timing-gated (tanks destroyed during the hold) and tick counts are platform-invariant, so if the port were fully tick-faithful upstream of this beat, an organic PC freeze should reproduce on N64 with the same play. Two live hypotheses: **(i) an upstream port divergence** (timing shim / scheduler phase / earlier state misread) opens a derail window on PC that never opens on N64 — in which case the freeze is a *port-exposed* artifact and the real fix is finding that divergence; **(ii)** it can occur on N64 but has simply never been observed (narrow window). **Discriminating test (revised 2026-09-22.)** Primary — **deliberate timing on an unthrottled emulator**; the derail window is *player-controllable*, so no instrumentation is needed. Per D321 the combat bit lands 212 ticks (~3.5 s) after the last tank destruction, and c78's vulnerable span runs from pre-aim (off=38) through the monologue loop (off=75, check re-evaluated continuously; ~22 s). So: on an **unthrottled emulator** (stable 60 Hz tick regime — the same regime as the port; Mupen64Plus-Next/Project64 at full speed) with save states, trigger the Ourumov scene, then destroy the last tank ~1–15 s into the monologue; repeat with fresh loads to sample the aim-variant lottery. **Freezes ≈ the port's forced-repro rate (~2/3)** → the race is reachable under stable ticks; "N64 never freezes" is an organic-timing/frame-drop story (hypothesis ii; watchdog = insurance, no port bug). **Never freezes across ~10 deliberate placements** → the mechanism differs environmentally (hypothesis i) and there is a genuine upstream port divergence to hunt. Control first: confirm the *port* freezes at the expected rate under the same deliberate timing (forced-repro probe can calibrate this headlessly). Secondary — **PRNG-stream A/B** (only if the emulator never freezes and hypothesis (i) needs hunting): the port already ships `GE_RSEED_LV` (`port/src/d318watchdog.c`) + DET seed logging — read `g_randomSeed` from N64 RAM `0x80024460` at a canonical moment (emulator memory viewer; that read is the only console-side step), inject it with `GE_RSEED_LV=<hex>@<tick>`, replay the same play, and compare DET lines: any divergence pinpoints the tick where the port's stream leaves the original's. The watchdog remains justified either way as a port-side liveness measure: it acts only in a state where the game otherwise hard-locks.

### Fix (port-side, `port/src/d318watchdog.c` — same pattern as D202 M-66b)

Per-tick check (hooked at the `g_GlobalTimer += g_ClockTimer` site in lv.c). Signature, all held for 600 consecutive ticks (10 s; the escape path resolves in < 2 s): chr 78 on list 0x0417 with offset in [321, 333), `actiontype == ACT_ATTACK`, `act_attack.entityid == 67` (targeting Trevelyan — legitimate combat at this offset targets Bond, ent=1), and chr 67 alive. On confirm: **re-initialize c78's attack via `sub_GAME_7F025560(c78, attacktype, entityid)`** — the same entry point the game itself uses for a fresh attack (chrlvTickAttack type_of_motion==2, chraction.c:7401). That runs `chrlvInitActAttack` → random variant + `modelSetAnimation(start_frame)`, breaking the pin; c78 then live-fires Trevelyan exactly like the natural escape path. One-shot per OCCURRENCE: after firing, the watchdog re-arms once the signature has been absent for 600 consecutive ticks (~10 s), so a later replay of Facility in the same session (AllUnlocked) is still covered — added 2026-09-19 during the v0.3.0 release review (M-192 item 3; previously one-shot per process, which would have left a replayed Facility unprotected). Logs `D318W:` lines for playtest audit; opt-out `GE_D318W=0`.

**Why not just kill Trevelyan:** first attempt applied the scripted headshot's own damage call (`handles_shot_actors(c67, 0x08, &zero, 0x06, FALSE)` — ai_22 off=333). c67 died, but a pinned attack has **no completion event tied to target death** — c78 stayed in ACT_ATTACK and the stop check still never passed (probe-verified: act=8 in 100% of samples post-kill vs 32/264 ACT_STAND samples in natural-escape runs). The attack state itself must be re-seeded.

**Why not an in-src fix:** making `actor_fire_or_aim_at_target_update` call `modelSetAnimation` would change behavior relative to N64 ground truth in *normal* play (Rule 2, no sign-off basis — there is no port divergence to correct). The watchdog is inert in every non-deadlocked state.

### Verification

- Forced-bit repros with the final watchdog: escape runs stay silent (c67 dies t≈2930-2960, 60× under threshold); a frozen run armed at t=2702, fired at t=3300, c67 died t=3570 from c78's own gunfire, and c78's post-recovery action profile (ACT_STAND/ATTACK/ATTACKWALK mix, moving) matches natural-escape runs.
- Plain headless Facility run (no env): zero D318 lines, no errors, clean shutdown.
- Interactive playtest (`scratch/d318_playtest3.log`, 2026-09-19): organic derail occurred; the run drew the escape variant, so c78 broke the pin on his own and killed Trevelyan within seconds. The watchdog detected the signature twice (t=7496, t=9270) but never confirmed — both windows cleared before 600 consecutive ticks → zero false positives in live play.
- Diagnostic probes removed (`port/src/d318probe.c`, `port/include/d318probe.h`, and the `#ifdef PORT` hooks in chrai.c/chraction.c/lv.c/model.c); only the permanent watchdog hook remains (lv.c).

**Status:** RESOLVED (2026-09-19). As-authored latent race documented; port-side watchdog ships by default. Trigger chain upstream of the derail (tanks → combat bit) fully mapped in D321 — PC behavior confirmed faithful to N64.
